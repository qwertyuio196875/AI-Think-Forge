# 领域文档

各工程技能在探索代码库时，应如何消费本仓库的领域文档。

## 探索之前，先读这些

- 仓库根目录下的 **`GLOSSARY.md`**，或者
- 仓库根目录下的 **`GLOSSARY-MAP.md`**（如果存在）：它指向每个上下文各一份 `GLOSSARY.md`。把与该主题相关的每一份都读一遍。
- **`docs/adr/`**：阅读涉及你即将动手的那个区域的 ADR。在多上下文仓库里，还要检查 `src/<context>/docs/adr/` 里针对特定上下文的决策。

如果这些文件有任何一份不存在，就**安静地继续**。不要指出它们缺失；也不要建议预先创建它们。`/domain-modeling` 技能（经由 `/grill-with-docs` 和 `/improve-codebase-architecture` 到达）会在术语或决策真正被定下来时，懒惰地创建它们。

## 文件结构

本仓库采用**单上下文**（single-context）布局：

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

## 使用术语表的词汇

当你的输出要命名一个领域概念时（在 issue 标题、重构提案、假设、测试名称里），请使用 `GLOSSARY.md` 中定义的术语。不要漂移到术语表明确回避的同义词上。

如果你需要的概念还不在术语表里，那是一个信号：要么你在发明这个项目不使用的语言（重新考虑），要么存在一个真实的缺口（把它记下来交给 `/domain-modeling`）。

## 标出 ADR 冲突

如果你的输出与一份现有 ADR 矛盾，就明确把它摆出来，而不是默默覆盖：

> _与 ADR-0007（事件溯源的订单）矛盾，但值得重新打开，因为……_
