# 0006. 引入「填充」阶段：逐章扩写正文，生成模块从此会调模型

- 状态：已接受
- 日期：2026-10-20
- 与既有声明的关系：推翻 `backend/app/generation/service.py:6-7` 的「本模块不做模型调用」这条被写进代码的架构契约

## 背景

本次需求要求：方案确认后，询问用户是否对大纲「填充」，转化为真正完整的 Word / PPT；生成文章时用户可选字数，生成 PPT 时用户可选页数。

核实到的代码事实：

- 结构化方案是**一整段 Markdown**（`plans.content_md`，`backend/app/db/database.py:79-87`），无章节字段；`backend/app/models/plan.py:24-34` 的 `Plan` 也没有章节数组；
- 生成链路**完全不调模型**：`generation/service.py` 把 `plan["content_md"]` 原样渲染成 docx（`service.py:68`），HTML 走 `deck.py` 的确定性渲染；
- 章节切分**已有三套互不一致的实现**：`grilling/revision.py:26` 的 `sections()`（认 1–6 级标题、同名章节键覆盖）、`generation/plan_document.py:38` 的 `parse_plan_blocks`（认 1–3 级、保留块序列）、前端 `frontend/src/utils/markdown.ts:107` 的 `splitPlanSections`；
- 模型客户端单次输出上限 `DEFAULT_MAX_TOKENS=4096`、超时 60 秒、无流式，`finish_reason=length` 直接抛 `ModelCallError`（`backend/app/providers/openai_client.py:28-33`）；
- `GenerationPanel` 在方案确认前不可见（`CreationView.vue:760-762` 的 `panelLocked`），确认是单向闸门；
- 无任何字数/页数参数，前端后端都没有；deck 的页数是 `slides_from_plan` 按 H1/H2 切页的副产品（`deck.py:100-143`），不可控。

结论：现有系统能生成**大纲文档**，但从没写过正文。字数控制不是加一个输入框，而是要先有一层「章节」，再有一次真正的写作调用。

## 决策

- **新增独立阶段「填充」**，独立接口 `POST /api/tasks/{id}/fill`，**不并入** `/generations`。`/generations` 保持「确定性渲染」的职责不变；填一次模型调用与之彻底分开，错误码与超时语义各自独立。
- **章节是一等实体**：新增 `plan_sections` 表，一章一行。章节来源是方案「章节」那一节的条目——**方案分节 ≠ 成品章节**（见术语表），不得用 `##` 切分结果直接当成品目录。`plan_v2` 提示词升级为 `plan-v3`，把该节固定为「每章一行：标题 + 要点 + 建议字数」，让切分确定可复现。
- **章节切分只保留唯一真源**：后端一个 `plan_sections` 模块负责切分与落库，前端只读展示。既有的三套切分器不得各自扩展成第四套；前端的 `splitPlanSections` 退为展示用途，不再产生权威章节。
- **切分后只做只读预览**（「将生成 N 章：1. 目标 约 300 字……」），提供「确认开始填充」与「返回修订方案」两个出口。**不提供改名、拖拽排序、增删章节**——那等于把 v1.1 的「方案直接编辑」提前，超出本次范围。想改章就回去走既有的对话修订。
- **填充入口是确认后的一条二选一横幅**（「填充为正文，产出完整 Word / PPT」/「仅导出大纲」），不弹模态框。面板在确认前本就不可见，横幅能表达「要不要填充」而不打断「确认 → 得到成品」的连续性，也不需要改动单向闸门。
- **逐章串行生成**：每章一次模型调用，上下文含「前情提要 + 本章要点 + 本章目标字数 + 剩余字数」。不整篇一次调用（长文必缩水且无法局部重试），不并发（各章互不承接会读成 N 篇短文拼接）。
- **前情提要**：每章写完后调一次小模型生成约 100 字摘要，累积成后续章节的承接上下文。它是生成期上下文，不进入方案、不进入成品。
- **字数按章分摊并可微调**：用户给全文目标字数，系统按章节权重给出每章建议字数，允许逐章改；生成时把余量反馈给后续章节；收尾时若总字数偏差超阈值，只对最短的章节重生成一次，不做整篇重生成。字数按**汉字**计，不含标点空白。
- **单章超出 4096 token 时的覆盖机制**：按段落分多次调用并拼接，每段累计校验字数与终止原因。`finish_reason=length` **仍然是硬错误**，绝不静默截断；覆盖机制不是优化项，是 5000 字以上能跑通的前置条件。
- **生成类调用超时分级**：填充的单章调用超时提高到 180 秒（渲染类调用维持现有 60 秒）。字数上限 20000，超出即拒绝并说明原因。
- **未填充导出保留**：跳过填充直接导出仍然可用，产物文件名以 `outline-` 前缀标识，与填充后的正文成品区分。两种成品并存，用户自己选。
- **可中断与断点**：填充任务可中断，已完成章节落库，恢复从下一章继续，界面显示「第 3/8 章 已完成」——这与术语表「任务」的既有定义一致。
- **现状不一致须收口**：`plan_v2` 里「章节」一节的既有渲染格式若无法解析出章节条目，填充入口**明确拒绝并提示返回修订方案**，不猜测、不按标题层级退化切分。

## 后果

- `generation/service.py:6-7` 那句「本模块不做模型调用」不再准确，须改口为「渲染不做模型调用；填充在 `fill` 模块」。这条契约是被显式推翻的，不是悄悄绕过的。
- 三套章节切分器成为明确的技术债。本次只立「唯一真源」原则，不重构既有三套；但任何新增功能都必须走 `plan_sections`，否则错位（「第三章内容写进第四章」）不可复现。
- `plan_sections` 让「逐章重生成」成为可能，也让「章节是唯一真源」成立。代价是方案修订后必须重新切分，切分结果与旧章节的对应关系须有明确规则（按章节标题匹配，匹配不上的一律废弃重建）。
- 填充是本系统第一次真正的写作调用，额度消耗与耗时都不再可忽略：8000 字量级 ≈ 6–8 次主调用 + 等量摘要调用。
- 前端 `GenerationPanel.vue` 需从「格式选择 + 生成按钮」扩为「横幅二选一 + 章节预览 + 字数/页数参数 + 逐章进度」。该组件已有约 1000 行，且项目无共享弹窗组件、无状态管理，本次是它第一次真正吃紧的地方。
- 与 ADR-0004 的耦合：页数的落地依赖「页面规划」这一中间产物，而页面规划发生在填充之后。也就是说**跳过大纲填充就没有页面规划，页数就不可控**——这条必须在界面上讲清，不能给用户「跳过填充也能精确控页数」的错觉。
