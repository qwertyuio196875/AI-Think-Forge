# 知识库夹具语料（fixtures/knowledge）

这批语料是 **RAG 的验收夹具，也是检索质量的回归测试集**。规格 #2「夹具」一节明确要求它们随仓库提交——没有这批语料，就没有判断检索好坏的依据。

## 用途

1. **验收**：知识库入库（分块数大于 0、状态为已入库）、检索命中（引用带文件名与段落号）、阈值行为（低相关度片段被丢弃）、降级行为（嵌入失败仍能返回结果）都要靠这批语料构造场景。
2. **回归**：检索参数（top-k=6、余弦相似度阈值 0.3、单次注入上限 3000 汉字）或分块参数（目标 1200 / 上限 1800 字符）一旦调整，用这里的 `index.json` 判据跑一遍，就能看出命中是否退化。

## 目录构成

共 15 份 `.md`，四类各若干：

| 类别 | `index.json` 里的 `category` | 份数 | 说明 |
| --- | --- | --- | --- |
| 技术文档 | `tech` | 4 | 流式生成的工程取舍、文档分块策略、提示词版本管理、汉字字数口径 |
| 产品说明 | `product` | 4 | 字数控制、演示文稿导出、知识库功能、模板与大纲导出 |
| 调研摘要 | `research` | 3 | AI 写作工具接受度、模板化写作痛点、引用可信度 |
| 访谈笔记 | `interview` | 4 | 内容团队负责人、技术写作者、自由撰稿人、客户支持负责人 |

## 为什么这样设计

- **有具体数字**：38 token/秒、1200 字符、0.3 阈值、2560×1440、412 份问卷……数字让「相关」和「恰好提到同一个词」区分得开。
- **口径前后不一致，且不一致本身是刻意的**：`04-tech-hanzi-counting.md` 说字数「只数汉字」，并明说旧文档里「按字符计」的说法已作废；`02-tech-document-chunking.md` 说早期分块参数是 800/1200 后改为 1200/1800。这些矛盾用来测试检索能否把「现行口径」与「历史口径」都召回，并靠相关度把现行的那份排在前面。
- **四类之间有语义交叉**：字数控制在产品说明、技术文档、访谈笔记里都出现；模板化在调研摘要与两份访谈里出现，且**立场相反**（企业内容团队认为是效率工具，自由撰稿人认为是思考的终点）；引用可信度同时出现在调研摘要与两份访谈里。这样才能测出「一个问题返回多个来源」，而不是永远只命中一份。
- **至少三处同主题不同说法**：模板的价值（`10` / `12` / `14`）、字数的痛点（`05` / `09` / `12`）、引用该给原文还是摘要（`11` / `15`）。

## 检索验收要点

- **能命中**：用 `index.json` 里的示例查询检索，期望命中的文件应出现在返回结果里，且引用带上文件名与段落号。
- **能排序**：同一主题有多个来源时，最贴题的那份应排在前面（例如问「模板是不是把文章写成了填空」，`14` 应排在 `12` 之前）。
- **能降级**：嵌入客户端抛错时，检索仍应返回结果，响应里带降级标记；此时命中质量允许下降，但不允许为空。
- **阈值行为**：拿一个与全库都无关的查询（例如「如何给猫剪指甲」），低于 0.3 的片段应全部被丢弃，宁可不给也不要塞弱相关内容；命中数不得超过 top-k=6。
- **注入上限**：单次注入总量不得超过 3000 汉字，超出时应截断而不是报错。

## 告诫

**不要修改这批语料的正文内容。** 任何一处措辞改动都会让回归基线失效——`index.json` 里的示例查询是按现有内容写的，改了内容，命中结果就不可比，此前记录的回归结论也随之作废。需要新增场景时请新增文件，并同步更新 `index.json` 与 `backend/tests/test_fixture_corpus.py` 里的份数契约，而不是改旧文件。

`backend/tests/test_fixture_corpus.py` 只钉**契约**（份数、类别分布、汉字数区间、`index.json` 与实际文件一一对应），不断言语料正文的具体句子——正文是夹具，不是被测代码。
