# 提示词版本管理：把版本号当接口版本对待

## 现状

提示词资产按模块分目录存放，方案、填充、页面规划、事实判定各一套。每一套的版本号写在文件头的一行注释里，形如 `plan-v3`、`fill-v2`。版本号会进三处：仓库提交信息、任务详情的「使用提示词」字段、失败日志。少写一处，事后就查不出某篇成品是哪个版本写出来的。

## 为什么要版本化

方案提示词从 v1 到 v3 改了两次。v2 把「章节」一节固定成每章一行，即标题加要点加建议字数，让章节可以确定性切分；v3 只把「风险」一节的示例改得更具体。前者属于破坏性变更，旧任务重跑会得到不同的章节数，因此 v2 上线时把已在跑的任务钉在 v1 上，新任务才用 v2。

## 一次事故

fill-v1 到 v2 把字数约束从「尽量接近」改成「不得超出 10%」，结果模型开始在段落末尾凑四字短语，读起来像公文。后来 v2 又加了一条禁止注水的负面示例，版本号没动——这是一次教训：改了行为就必须升版本，哪怕只改一句话。

## 灰度

提示词变更按任务 id 取模 10 做灰度，一成新、九成旧，观察两天。灰度期间两套提示词的成品都会落库，靠版本字段区分。没有指标看板，判断依据是抽读二十篇成品，加上用户投诉。

## 不做的事

不做提示词的可视化编辑，不做在线热更新。改提示词就是改代码、走评审、留下 diff。理由很直白：提示词是本系统里唯一直接决定输出质量的东西，它应该和代码一样有历史。
